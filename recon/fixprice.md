# Fix Price (fix-price.com) — разведка 2026-10-31

С russia-03 (дата-центр) API отвечает 200 на голый `curl` без cookie и
токенов. Заголовков Cloudflare (`cf-ray`, `server: cloudflare`, `cf-mitigated`) нет
ни у `api.fix-price.com`, ни у `fix-price.com`. За ~200 запросов при ~2,5 rps не было
ни 403, ни 429, ни капчи. Playwright не нужен, хватает httpx. Таймауты при этом
бывают: у SSR-страницы один раз из пяти, а 600 KB `/location/city` один раз пришли
обрезанными. Поэтому нужен ретрай и таймаут от 60 с на большие ответы.

## База и заголовки

`https://api.fix-price.com/buyer/v1` — API фронта (Nuxt 2, axios); перед ним стоит KrakenD.
Достаточно:

```
x-city: <cityId>          # обязательный по смыслу: от него зависят цены и ассортимент
x-language: ru
Accept: application/json
Content-Type: application/json   # для POST
x-pfm: <pfm магазина>     # необязательно, выбранный магазин самовывоза
```

Фронт шлёт ещё `x-key` (одноразовый токен, сервер возвращает новый в каждом ответе
и в cookie `token`), `x-order-type: combined`, `x-logged`, `x-client-route`.
Ни один из них не нужен. Без `x-city` берётся Москва (`3`).

Город фронт держит в cookie `locality` (`{"city":"Москва","cityId":3,…}`) и переносит
его в заголовок `x-city`. Магазин самовывоза лежит в cookie `x-pfm` и уходит в
заголовок `x-pfm`. `/buyer/v2/geo/ip` с IP дата-центра отвечает `400 Данные не найдены`,
город по IP не определяется.

## Город и магазин

**Цена зависит от города (ценовой зоны), не от магазина.** Проверено полным
листингом «Кондитерских изделий» (450 товаров) и «Молочных продуктов»:

- Москва = Казань = Новосибирск = Санкт-Петербург: у всех общих товаров одинаковые
  `price` и `specialPrice`;
- Владивосток, Якутск, Петропавловск-Камчатский и Калининград: цена другая у 100%
  общих товаров;
- два магазина Москвы (`x-pfm` `H456` и `H914`) и магазин Казани `D215` дают те же цены,
  что и город без `x-pfm`: 472 и 404 общих товара, 0 расхождений.

Зоны по Choco Pie 360 г (`/product/sku/1950692`):

| Цена | Города |
|---|---|
| 174,50 | Москва, Казань, СПб, Новосибирск, Красноярск, Омск, Тюмень, Сочи |
| 200,00 | Мурманск, Архангельск |
| 212,50 | Калининград |
| 225,00 | Иркутск, Чита, Улан-Удэ, Сургут |
| 265,00 | Владивосток, Находка, Уссурийск, Хабаровск, Норильск |
| 307,50 | Якутск, Магадан, Петропавловск-Камчатский |

Справочника «город → зона» в API не нашлось. Хранить цену по городу; одинаковые зоны
схлопнутся сами. Достаточно обойти по одному городу на зону, но список зон надо
выводить сравнением цен.

**Ассортимент** зависит и от города, и от магазина:

- без `x-pfm`: Москва 450 кондитерских, Казань 371, Якутск 255;
- с `x-pfm` у каждого товара появляется `availabilityType`: `primary` (есть в
  магазине) или `secondary` (под заказ в магазин). В `H456` 287 primary / 185 secondary,
  в `H914` 86 / 386. `x-count` с `x-pfm` больше (472 против 450), потому что
  добавляются товары под заказ.

Если ассортимент нужен по точке, листинг надо гонять с `x-pfm`. Если только цены,
хватает одного прохода на город.

### Магазины

| Что | Запрос |
|---|---|
| Все магазины | `GET /store` → 7 239 точек (3,3 MB), 1 849 `cityId`. Поля: `id`, `pfm` (код магазина, идёт в `x-pfm`), `address`, `shortAddress`, `latitude`, `longitude`, `cityId`, `isActive`, `canPickup`, `warehouse`, `temporarilyClosed`, график, `metroStations` |
| Магазины города | `GET /store?cityId=40` → 40 точек Казани (Москва — 352) |
| По координате | `GET /store?latitude=…&longitude=…` → 35 точек вокруг (радиус не выяснен). Надёжнее брать весь `/store` и искать ближайшие локально |
| Один магазин | `GET /store/{id}` |
| Остатки товара по магазинам | `GET /store/balance/{productId}` (+ `x-city`, опционально `?canPickup=&inStock=`) → все точки города, `count` = остаток в штуках. Для Москвы ответ на 220 KB |
| Города | `GET /location/city` → 1 914 городов (600 KB): `id`, `name`, `regionTitle`, `latitude`, `longitude`, `fias`, `countryId` (2 — Россия, 3 — Казахстан, …). `GET /location/city/{id}` — один город. `GET /location/country`, `GET /location/region?countryId=2` |

`find_stores(lat, lon)`: загрузить `/store` (раз в сутки), выбрать ближайшие точки
и взять у них `cityId`. Цену хранить по `cityId`, магазин нужен только для ассортимента.

## Эндпоинты каталога

| Что | Запрос |
|---|---|
| Дерево категорий | `GET /category/menu` → `[{id,title,alias,url,adult,productCount,items:[…],products}]`. 30 корней, среди них промо-подборки («Магия Halloween!», «Спец цена по карте», «Новинки», «Сейчас покупают»). «Продукты и напитки» (`id 2004`, `url produkty-i-napitki`) — 18 листьев, глубина 2: Кондитерские 450, Бакалея 111, Чай/кофе/сахар 111, Закуски 90, Газировка 72, Мороженое 66, Напитки 46, Плоды/овощи/грибы 34, Жвачка 30, Молочные 29, Вода 24, Хлебобулочные 23, Соки 20, Рыбные консервы 15, Мясные 12, Соусы 8, БАДы 1, Детское питание 1 |
| Листинг | `POST /product/in/{category.url}?page=N&limit=L&sort=sold`, body `{"category":"<category.url>","brand":[],"badge":[],"price":[],"isDividedPrice":false,"isSpecialPrice":false}` → массив товаров; общее число в заголовке **`x-count`** |
| Карточка | `GET /product/sku/{id}` (+ `x-city`) |

Пагинация: `page` с 1, `limit` до **99**. При `limit ≥ 100` сервер молча
возвращает 28 штук. Конец — когда `page*limit ≥ x-count` или пришёл пустой массив.

В корне «Продукты и напитки» `x-count = 1218`, а сумма по листьям — 1143:
~75 товаров не лежат ни в одном листе. У товаров в листинге `category.id` почти всегда
`2004` (корень), иногда `2528` («Спец цена по карте»). Лист из поля не узнать, его
даёт только обход листьев. Поэтому: обойти 18 листьев (лист = категория товара), потом
корень, чтобы добрать остаток.

Остальные корни (бытовая химия, косметика, игрушки, дом, одежда и т. д.) устроены
так же, сейчас не нужны.

## Поля

Листинг: `id` (= `sku`, int), `title`, `price` (**рубли строкой**, `"69.00"` —
×100 в копейки), `specialPrice` (`null` или `{"price":"169","active_to":"2999-12-31 …"}`;
это цена по карте Fix Price, бейдж `special_price` «спец цена»; в Москве у 81 из 450
кондитерских), `minPrice`/`maxPrice` (равны `price`), `unit`/`unitPrice` (весовых нет,
пусто у всех), `inStock` (int; с остатками `/store/balance` не сходится, судя по всему
это доступное к заказу количество, а не наличие на полке), `availabilityType`,
`variantCount`, `images[].src`, `url` (страница: `https://fix-price.com/catalog/{url}`),
`brand{id,title}`, `adult`, `badges[]`, `isNew`/`isHit`/`isPromo`, `feedback.rating`.
Старой («зачёркнутой») цены нет: скидка бывает только в виде `specialPrice`.

Карточка `/product/sku/{id}`: верхний `price` равен `null`, цены лежат в `variants[]`
(`price`, `fixPrice`, `count`, `barcode` = EAN, `dimensions.weight` — вес брутто в г).
`specialPrice` в карточке нет, брать его из листинга. Дальше:

- `brand{title,isSTM}`, `description`;
- `properties[]`: `prodCountry`, `manufacturer`;
- `extraDescriptions[]` по `alias`:
  - `composition` — «Состав»;
  - `nutritionalValueSeparated.value` = `{energyValue, protein, fats, carbohydrates}`
    (строки, на 100 г);
  - `nutritionalValue` — то же текстом;
  - `manufacturerAddress`.

Вес нетто отдельным полем не приходит, только в `title` («…, 200 г», «973 мл»,
«25 пакетиков, 37,5 г»). В `variants` обычно два варианта одного товара (EAN и
«Ассортимент» с `barcode = sku`), цена у них одинаковая.

SSR-страницы `fix-price.com/catalog/...` содержат первую страницу товаров (Nuxt
`window.__NUXT__`). Это запасной путь, если API закроют.
